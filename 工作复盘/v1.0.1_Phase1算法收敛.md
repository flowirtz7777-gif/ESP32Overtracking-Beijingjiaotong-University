## 三、关键技术成就（论文/答辩可用）

### 1. 物理建模严谨性

- 完整推导含鞍座偏置 `l_h` 耦合的挂车横摆率
- 直行 dφ/dt = -vB·sin(φ)/L，时间常数 τ = L/vB，与一阶阻尼系统一致
- HTML 仿真器与 MATLAB 主预测器**物理方程逐字对齐**（4 处同步修正）

### 2. 多边形语义创新

- 用户定义"右沿外缘扫掠"：H_right 弧 + T_right 反弧 + 起止两根直车身边
- 物理直觉指出"外甩三角是车走过的空地"
- B2 方案用 `polyshape Simplify` 偶奇规则自动剔除外甩三角

### 3. BodyNow 兜底（v1.0.1 关键漏洞修复）

- 暴露并修复"目标已被外缘扫过、当前在挂车车身下"的漏判
- 4 顶点矩形即可，移植到 ESP32 < 10 行代码
- 论文里可作为"算法严谨性"的具体案例

### 4. R3 反例诊断

- 用 TTC 复盘工具发现 `alpha_dot=0` 假设的局限
- **严格区分"在线主判警口径"和"复盘评估口径"** —— 这条边界划分是工程严谨性的体现
- R3 反例数据（坐标、TTC 时间序列）已固化到文档，可复现

### 5. 工具链完整性

- 三个独立 GUI（PID 导出器 / Python 滑条 / Electron 复盘）
- 自动归档（`Matlab/runs/<时间戳>__<csv名>/`）
- AI 协作文档（CLAUDE.md / AGENTS.md / TODO.md）

## 四、风险与注意点

### 风险 1：Phase 2 移植到 ESP32 的等价性验证

- 必须建立 C++ vs MATLAB 的"相同输入 → 多边形顶点误差 < 1mm"门控
- 浮点单精度可能导致小累积差异，需要单元测试

### 风险 2：HTML 端的"轴距硬修正"

- 当前导致 4-5mm 位置门控不通过
- 不影响算法正确性（只是 PID 仿真器自身的离散化方式不严谨）
- 但会让 demo 报告里"未通过门控"看着不舒服

### 风险 3：实车 α/φ 标定

- 占位标定 `0..4095 → 0..2π` 完全没经过真实校准
- 实车初次接入时**会出现非常大的初始误差**，要给标定脚本和"零位记录"功能预留接口

### 风险 4：硬件团队进度

- 当前所有进展都在算法层，硬件那边（PCB / 接线 / 雷达安装位置）相对滞后
- 建议：尽早确定 PCB 终版 + LD2450 安装支架 + α/φ 传感器机械安装

## 七、对话过程的关键决策点（供未来回顾）

- **建模哲学转向**：从"控制问题"重定义为"短时风险预测问题"
- **PID 模型重新定位**：从"在线判警核心"降为"工况生成器 + 对照模型一"
- **不引入大模型**：明确 ESP32 + 规则化算法的路线，避免黑盒+算力陷阱
- **双 MCU 方案选择**：ESP32-S3 + OpenMV 而非单板计算机，保留低成本量产路径
- **真值 TTC 与在线判警的边界**：复盘工具不能反向污染主算法
- **目标定义的迭代**：从"挂车后角偏移"逐步收敛到"扫掠区几何中心"，9 个版本

这一版的核心教训是：**算法语义反复迭代时，必须有第三方工具（TTC 复盘软件）作为外部裁判，否则容易陷入"我以为对了"的自我循环**。
